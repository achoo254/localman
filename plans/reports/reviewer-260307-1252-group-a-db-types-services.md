## Critical Issues (must fix before next phase)

- **[backup-service.ts:45-64] Import is NOT atomic — data loss window exists.**
  The import uses two separate transactions: first clears all data, then re-inserts. If the process crashes or the second transaction fails after the first commits, all user data is permanently gone. The clear and insert for related stores must be wrapped in a single transaction, or use a "delete old, insert new, verify" pattern. Dexie supports opening a transaction across all stores simultaneously via `db.transaction('rw', [all tables], ...)`.

- **[collection-service.ts:41-47] Cascade delete is NOT atomic.**
  `remove()` deletes folders, then requests, then the collection in three separate awaits — no transaction. A crash mid-sequence leaves orphaned records. Wrap all three operations in `db.transaction('rw', db.collections, db.folders, db.requests, ...)`.

- **[folder-service.ts:46-56] Recursive folder delete is NOT atomic and has wrong semantic.**
  The recursive `remove()` does not delete child requests — it orphans them by setting `folder_id = null`. This is likely unintentional for a delete cascade. Also, each recursive level opens its own un-transacted DB calls. Define the correct semantic (delete or orphan child requests?) and wrap in a single transaction. If orphaning is intended, the name `remove` is misleading.

- **[response-store.ts:61] Silent history failure swallows all errors, including IndexedDB quota exceeded.**
  The empty `catch {}` means if IndexedDB storage is full, or the DB is corrupted, the error disappears silently. At minimum, `console.warn` or report to a global error boundary so it can be diagnosed.

## Important Issues (should fix soon)

- **[request-store.ts:73] `closeTab` loses `activeRequest` incorrectly when switching tabs.**
  Line 73: `activeRequest: nextActive && get().activeRequest?.id === nextActive ? get().activeRequest : null`
  When closing a non-active tab, `nextActive` will not equal `activeRequest.id`, so `activeRequest` is set to `null` even though the user hasn't changed tabs. The condition should be: if closing the active tab, the new active request must be loaded; if not, keep the current `activeRequest` unchanged.

- **[request-store.ts:79] `setActiveTab` does not load request from DB.**
  When `id` differs from the current `activeRequest.id`, it sets `activeRequest` to null instead of fetching from DB. The tab is now "active" but showing nothing. `setActiveTab` should call `loadRequest(id)` when the ID changes.

- **[request-store.ts:93-113] `createNewRequest` duplicates request object construction.**
  It manually constructs a full `ApiRequest` (with `newId`, `now`, etc.) then calls `requestService.create(request)` passing the full object. But `requestService.create` expects `Omit<ApiRequest, 'id' | 'created_at' | 'updated_at'>` and generates those fields itself — the IDs created here are discarded and new ones are generated by the service, creating a mismatch. The store should pass only the partial data and use the returned value.

- **[environment-service.ts:51-56] N+1 write pattern in `setActive`.**
  Updates every environment row individually inside a loop. For large environment lists this fires N separate DB writes. Use `bulkPut` with a mapped array instead.

- **[collections-store.ts:15-17] `loadExpanded()` always returns an empty Set.**
  The sync stub `loadExpanded()` exists alongside `loadExpandedAsync()` and is called in the initial state (`expandedIds: loadExpanded()`). The async version is only used in `hydrateExpanded()` which must be called separately. If `hydrateExpanded()` is never called on mount, the expanded state is never restored. This should be documented clearly or the store initialization should ensure hydration is triggered.

- **[history-service.ts:21-34] In-memory filtering after ordering loses limit correctness.**
  `query()` calls `orderBy('timestamp').reverse()`, then applies JS filters for `requestId`, `method`, `statusCode`, and only then `.limit(limit)`. The limit is applied after in-memory filtering of an already-fetched cursor. For large history tables, this loads potentially thousands of rows into memory before filtering. Use Dexie's index-based `where` clauses where possible, at least for `request_id` which has an index.

- **[folder-service.ts:13-16] `getChildren` loads entire collection's folders then filters in JS.**
  All folders for a collection are fetched with `toArray()` and then filtered for `parent_id`. With the compound index `[collection_id+parent_id]` already defined in the schema, this should use `db.folders.where('[collection_id+parent_id]').equals([collectionId, parentId ?? null])` for efficiency.

- **[request-service.ts:13-16] `getByFolder` same issue as `getChildren` above.**
  The compound index `[collection_id+folder_id]` exists but is unused. Direct index query would avoid scanning the full collection's requests.

- **[auth-handler.ts:17-21] Basic auth with empty username or password is accepted.**
  `auth.username != null && auth.password != null` passes for empty strings `""`. An empty Basic auth header is functionally useless and probably a user error. Check `.trim()` length or at least emit a warning.

- **[request-preparer.ts:46-48] `form-data` (multipart) body is silently dropped.**
  `case 'form-data': return undefined` with no explanation other than a stub comment. This is a supported body type in the type system. Either handle it or throw an explicit "not yet implemented" error so the user gets feedback instead of silently sending no body.

- **[tree-builder.ts:40] Non-null assertion on potentially missing collection.**
  `collections.find(c => c.id === collectionId)!` — if `collectionId` references a collection not in the array (e.g., stale data), this crashes with a runtime null-dereference. Add a null guard.

- **[use-auto-save.ts] Timer does not reset when `isDirty` flips back to false then true rapidly.**
  Each `isDirty` change restarts the timer. But `isDirty` is a boolean — it only changes from false→true, not repeatedly. In practice, `updateActiveRequest` always sets `isDirty: true`; subsequent calls don't re-trigger the `useEffect` because the dep value doesn't change. The auto-save will only fire once per "dirty session". If a save completes (sets `isDirty: false`) and then the user edits again (sets `isDirty: true`), the effect re-fires correctly. This works but it's subtle — a comment explaining this would help.

## Minor Issues (nice to have)

- **[models.ts:62] `HistoryEntry.id` typed as `number | undefined`** but all other entity IDs are `string`. The `++id` auto-increment is fine for history, but the optional `id` means TypeScript won't catch accidental use of undefined id in `getById`. Narrow it to `number` in the return context or make it required after insertion.

- **[common.ts:29] `oauth2Config: Record<string, string>`** is too loose. A dedicated `OAuth2Config` interface with known fields (`access_token`, `token_type`, `refresh_token`, `expires_in`, etc.) would improve correctness.

- **[db/index.ts]** Does not re-export services — consumers must import directly from `./services/<name>-service`. This is fine architecturally (explicit imports are better), but the file comment says "Import services from ./services/<name>-service" — it should also export utils (`newId`, `now`) for convenience or document they're internal only.

- **[http-client.ts:69-74] `bodySize` is computed from the full text, not the truncated body.**
  `bodySize = new Blob([text]).size` uses the full text — this is correct for reporting actual response size. But it creates a temporary Blob in memory just to measure byte length, duplicating the string. For ASCII-only content, `text.length` suffices; for UTF-8 correctness, `new TextEncoder().encode(text).length` avoids the Blob allocation.

- **[http-client.ts:41-46] Cookie fallback uses `headers.get('set-cookie')` which only returns first cookie.**
  The `getSetCookie()` fallback is correct, but the fallback-of-fallback on line 43-45 (`headers.get('set-cookie')`) only retrieves the first value when multiple `Set-Cookie` headers exist (standard HTTP behavior for `Headers.get()`). This is a known browser limitation; the comment should document it.

- **[url-params.ts:31] `url.split('?')[0] ?? url`** — the `?? url` can never be reached because `split()` always returns at least one element. Minor dead code.

- **[collections-store.ts:82] `Math.max(...list.map(...))` will throw a stack overflow** for very large collections (thousands of items). Use `list.reduce((max, c) => Math.max(max, c.sort_order), -1)` instead.

- **[lib.rs:3-5] `greet` command is scaffolding leftover** and should be removed before Phase 2 work begins to keep the Tauri command surface clean.

- **[db.integration.test.ts:14-15] Duplicate import lines.**
  Lines 14 and 15 both import from `'../types/common'` — they can be merged into one import statement.

- **[tree-builder.test.ts]** Only covers flat collections and search. No test for nested folders, `folderHasMatch` logic, or `requestCount` correctness.

- **[auth-handler.test.ts]** No test for `oauth2` type or empty/whitespace bearer token (which should return `{}`).

## Positives (good patterns worth keeping)

- DB schema uses compound indexes `[collection_id+parent_id]` and `[collection_id+folder_id]` — correct design even if services don't use them yet.
- `useAutoSave` pattern with `isDirty` flag is clean and avoids unnecessary DB writes.
- `prepareRequest` cleanly separates concerns: URL building, header merging, auth injection, body serialization.
- `buildTree` correctly propagates ancestor visibility on search (parent shows when child matches).
- `backup-service.exportAll` uses `Promise.all` for parallel DB reads — good performance practice.
- `getAuthHeaders` has a proper exhaustive switch with `default: return {}` fallback — defensively correct.
- History response body is capped at 50KB in `response-store` — prevents IndexedDB bloat.
- `use-collection-tree` properly memoizes with `useMemo` to avoid re-running `buildTree` on every render.
- Rust: `lib.rs` correctly uses `#[cfg_attr(mobile, tauri::mobile_entry_point)]` for cross-platform entry.

---

## Summary

The foundational layer is structurally sound — types are clean, the DB schema is well-designed, and the service API surface is consistent. The primary concern is atomicity: three separate places perform multi-step DB mutations without transactions, which creates real data loss/corruption risk if the app crashes mid-operation. The `closeTab`/`setActiveTab` logic in the request store has a correctness bug that will cause blank UI states. The history query's in-memory filtering and two services ignoring their own compound indexes are performance issues that will become visible as data grows. Fix the transaction issues before the next phase ships any user data.

## Unresolved Questions

1. Is the "orphan requests when folder is deleted" behavior in `folder-service.remove` intentional? The current implementation moves requests to root (sets `folder_id = null`) rather than deleting them — this should be a documented design decision.
2. Is `hydrateExpanded()` called on app startup? If not, the sidebar expanded state is never restored from settings.
3. What is the planned approach for `form-data` multipart body support — Tauri's native HTTP plugin, or browser FormData? This affects how `buildBody` handles `case 'form-data'`.
